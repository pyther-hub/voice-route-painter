Voice Route Painter

Hold Space and say "Lucknow se Jaipur jaana hai, beech mein Agra". An AI agent draws the road route on a map of India. Change it by voice or text: "Agra hata do", "wapas pehle jaisa kar do".

The focus is the agent layer: an orchestrator with a goal and tools but no scripted flow, with tracing, evals, guardrails and measured experiments.

Design principles

  1. Goal and tools, not a flow. The prompt states the goal, facts and rules. There is no step list and no phrase-to-tool table.
  2. One write path. Only update_state() changes the trip. It bumps the version, saves undo history and pushes the full state. It ignores writes from a run that is no longer current.
  3. The frontend is dumb. On every message the browser calls render(state) and redraws. It holds no keys and calls no third-party APIs.
  4. Every tool call goes through a gateway. It validates arguments, enforces limits, runs the tool and records a span. Errors say what to do next.
  5. Everything is a span. STT, agent runs, LLM calls and tool calls record input, output, timing and status. Raw audio and keys are never stored, and tracing never breaks a turn.
  6. Limits live in code. Caps on steps, tokens and spend, and timeouts on every external call.
  7. Add agents only for a measured reason. It is still one agent with tools. A split needs a trace or eval that shows a problem it would fix.

The agent

  • Tools: resolve_place, set_route, add_stop, remove_stop, undo, ask_user, reply, suggest_enroute_places, suggest_nearby_places.
  • Input to the model: a JSON object with the current trip, any pending question, the last mentioned place, the user's input and the last 3 turns.
  • Detected places (prompt v25): before the first LLM call, code finds places named exactly in the text and looks them up. The model uses those ids directly and calls resolve_place only for typos and colloquial names.
  • Guardrails in code: at most 2 new stops the user never named; no duplicate stops except a round trip's return; a step cap; suggested places must come from the tools, not from the model's memory.
  • No LLM call needed for: undo, redo, removing a stop, adding a suggested place, loading a shared link, switching model.
  • Spend caps: per session and per day, in USD, checked before every LLM step and valid for every model.

Routing and map

  • The graph holds motorway, trunk and primary roads from OpenStreetMap: 118k nodes and 170k edges. A* finds the fastest route and reports its km.
  • Most legs are within 5% of Google's distance. Jaipur to Kochi is 2,363 km against about 2,400 km.
  • The process uses 81 MB at start, because the graph sits in packed arrays and loads in 0.1 s.
  • Map road layers are ranked by highway number and load by zoom level, in 2° tiles, so zooming stays smooth.

Product hygiene

Origin check on the WebSocket, per-IP rate limits (12 paid messages a minute), caps on sockets per IP and on open sessions, USD spend caps, a 300-character input limit, server-side keys, and a trace viewer behind a key.

Evaluation and results

Eval set

52 sessions and about 80 turns: creates, edits, undo, round trips, typos and aliases, vague asks, guardrails and suggestions. Each turn is checked on stops, order, replies and whether the agent asked.

First full run (prompt v17, gpt-5.4-nano): 76 of 80 turns and 46 of 50 sessions passed, $0.048 in total, median latency 4.2 s. The failures led to prompt v18.

Experiments

The dataset is 300 hand-written single-turn examples with gold edits and gold place mentions. Each arm ran once, and intervals reflect spread across examples, not run-to-run LLM noise.

Decisions from the results

  • Keep prompt v25 (exact detected places).
  • Move to batched edits (B or C) next.
  • Default to DeepSeek for cost, with Gemma as the fast option.

Limitations

  • Each experiment arm ran once, so LLM run-to-run noise is not measured.
  • exp-01 and exp-02 used DeepSeek only.
  • The Groq comparison is incomplete because of its daily token cap.
  • No accounts or saved trips.
  • Not yet deployed over HTTPS.
